# knowledge_shelf_query 部署与更新操作文档

## 一、文件说明

| 文件 | 用途 | 更新频率 |
| --- | --- | --- |
| `knowledge_shelf_query_runtime:v1.1.0` | Python 3.12、Docker CLI 和 Compose 运行环境 | 仅环境变化时更新 |
| `knowledge_shelf_query_<版本>.bin` | 应用代码、页面和静态资源 | 每次源码变化时更新 |
| `config/` | 下单、仪表板、测试单等运行配置 | 设备本地保存 |
| `robot_keyboard.env` | 机器人键盘配置 | 按现场需要更新 |

飞书规则源文件为 `ksq/feishu/rules.json`。打包后对应部署目录中的 `config/feishu_rules.json`，容器内路径为 `/app/feishu_rules.json`。现场修改规则文件后执行 `bash start.sh restart`，规则会在服务启动时重新加载和校验。

`.bin` 是由 ZIP 格式封装的单文件 Python 应用包，可在相同 Python 运行时中跨 x86 和 ARM 使用。它不是原生机器码，也不用于源码加密。

## 二、首次准备运行时镜像

运行时镜像基于 `python:3.12.13-slim-bookworm`，内置 Docker CLI `27.5.1` 和 Docker Compose `v2.33.0`，不包含项目源码、编译工具和第三方 Python 包。当前 ARM64 构建在本机显示约 `359 MB`，原运行镜像约 `2.17 GB`。

目标设备需要安装 Docker Engine，并提供 `docker compose` 或 `docker-compose` 命令供启动脚本使用。容器通过 `/var/run/docker.sock` 调用宿主 Docker；Docker CLI 和 Compose 已包含在镜像中，不需要挂载宿主机二进制文件。

只有基础镜像、Python、Docker CLI、Compose 或其他系统依赖发生变化时才需要重新构建运行时镜像。

在开发机执行：

```bash
bash devOps/build_push_aarch64.sh v1.1.0
```

生成并推送：

```text
hub.noematrix.cn/pharmacy/knowledge_shelf_query_runtime:v1.1.0
```

目标设备首次启动时会自动拉取该镜像；后续更新应用包不会再次拉取。

网络不稳定时，可在开发机将 ARM64 运行镜像导出并只传输一次：

```bash
docker save hub.noematrix.cn/pharmacy/knowledge_shelf_query_runtime:v1.1.0 \
  | gzip -1 > knowledge_shelf_query_runtime_v1.1.0_arm64.tar.gz

scp knowledge_shelf_query_runtime_v1.1.0_arm64.tar.gz nvidia@<设备IP>:~/
```

在目标设备导入：

```bash
gzip -dc knowledge_shelf_query_runtime_v1.1.0_arm64.tar.gz | docker load
```

导入后的镜像标签与 `docker-compose.yml` 一致，执行 `bash start.sh start` 时不会再拉取。

## 三、首次部署

### 3.1 开发机打包

```bash
bash deploy/make_package.sh v1.2.5
```

生成两个文件：

```text
deploy/dist/ksq_deploy_v1.2.5.tar.gz
deploy/dist/knowledge_shelf_query_v1.2.5.bin
```

部署包目录结构：

```text
ksq_deploy_v1.2.5/
├── bin/
│   └── knowledge_shelf_query.bin
├── config/
│   ├── dashboard_settings.json
│   ├── dashboard_active_order.json
│   ├── test_order_state.json
│   ├── order_config.json
│   ├── order_config.prod.json
│   └── feishu_rules.json
├── data/
│   ├── current/
│   │   ├── knowledge/
│   │   └── config_pnp/
│   └── backups/
├── docker-compose.yml
├── robot_keyboard.env
└── start.sh
```

### 3.2 上传到目标设备

```bash
scp deploy/dist/ksq_deploy_v1.2.5.tar.gz nvidia@<设备IP>:~/
```

### 3.3 目标设备启动

```bash
tar xzf ksq_deploy_v1.2.5.tar.gz
cd ksq_deploy_v1.2.5
./start.sh
```

启动时会检查应用包、业务数据目录和运行时镜像，并自动创建部署目录的 `data/`；`current/` 和 `backups/` 随加载生成。本地没有运行时镜像时才会拉取；如果存在同名旧容器，会先停止并移除旧容器，再启动当前部署包，否则直接启动。

启动后访问：

```text
http://<设备IP>:8765
```

### 3.4 非默认数据目录

默认目录：

| 数据 | 默认设备路径 |
| --- | --- |
| `config_pnp` | `/home/nvidia/compiled/PNPApp_deploy/config_pnp` |
| `KNOWLEDGE_DIR`（Knowledge 根） | `/home/nvidia/compiled/VfmApp_deploy/model/templates` |
| 默认实际目录 | `/home/nvidia/compiled/VfmApp_deploy/model/templates/knowledge` |

路径不同时执行：

```bash
CONFIG_PNP_DIR=/实际/config_pnp \
KNOWLEDGE_DIR=/实际/model/templates \
bash start.sh start
```

`KNOWLEDGE_DIR` 指向包含多个场景目录的 `model/templates` 根目录。启动脚本将它挂载到容器 `/data/knowledge`；默认「一键加载」读取 `/data/knowledge/knowledge`，页面也可以填写根下任意相对目录（例如 `pnp_percept/templates_260827` 或其 `.../knowledge` 子目录），不读取 VfmApp `config.yaml`。填写场景目录时会自动定位其 `knowledge` 子目录。根目录不存在时启动会终止；默认子目录不存在时仅提示警告，仍可在页面选择其他目录。

旧部署目录若仍把 `KNOWLEDGE_DIR` 配置为 `.../model/templates/knowledge`，启动脚本会自动提升到 `templates` 根目录并提示；其他自定义路径请改为新的根目录写法。

只切换同一根目录下的场景目录时，无需改挂载或重启，在页面填写新相对路径后点击「加载数据」；更换 `KNOWLEDGE_DIR` 根目录才执行 `bash start.sh restart`。默认目录的 JSON 内容更新后，页面点击「一键加载」即可。

### 3.5 工作副本和备份

`KNOWLEDGE_DIR` 和 `CONFIG_PNP_DIR` 仍是加载来源。应用将所需文件复制到 `data/current/knowledge`、`data/current/config_pnp` 后使用，本机路径、一键加载、ZIP、导入和重新加载都显示进度；不修改这两个源目录中的文件。

部署配置在服务的 `volumes` 中增加以下挂载，持久化当前工作副本和备份：

```yaml
- ./data:/app/data
```

手工维护部署文件时，在部署目录执行 `mkdir -p data`。升级用户必须同步新版 `docker-compose.yml` 和 `start.sh`，或使用完整部署包；只更新 `.bin` 不会添加该挂载。容器重建前确认已有工作副本和备份已保存在部署目录的 `data/` 中。

每次成功切换数据前，上一份工作副本移至 `data/backups/YYYYMMDD_HHMMSS_ffffff`（末段为六位微秒）。每天服务本地时间 `00:00` 清理此前的备份，保留最新一份备份和当前使用文件；服务启动时补清理过期备份，当天生成的备份继续保留。标准容器时区由 `TZ` 配置，默认 `Asia/Shanghai`。

查询页面仅允许编辑库位、货架属性、挡板高度，保存目标是 `data/current/config_pnp` 中的工作副本；Knowledge、工具、不可处理、闭环吸取只读。重新加载本机路径会重新复制源文件，覆盖工作副本中的库位修改，需保留时先导出。

## 四、日常源码更新

源码、HTML、CSS 或 JavaScript 变化时，通常只更新 `.bin`，无需构建或拉取镜像。首次启用宿主机文件与终端连接时，必须同时同步 `start.sh`、`host-files.sh`、`docker-compose.yml`；后续更新会一并更新宿主机连接进程使用的代码。

版本若同时修改了 `start.sh` 或 `docker-compose.yml`（例如 Knowledge 挂载方式变化或新增 `./data:/app/data`），必须更新完整部署包或手工同步这两个文件；`start.sh update <应用包.bin>` 只替换应用包，不会更新部署配置。

### 4.1 开发机构建应用包

```bash
python3 deploy/build_app_bin.py v1.2.6
```

输出：

```text
deploy/dist/knowledge_shelf_query_v1.2.6.bin
```

构建完成时会显示文件大小和 SHA256。

### 4.2 上传应用包

```bash
scp deploy/dist/knowledge_shelf_query_v1.2.6.bin \
  nvidia@<设备IP>:/tmp/
```

### 4.3 目标设备更新

在当前部署目录执行：

```bash
bash start.sh update /tmp/knowledge_shelf_query_v1.2.6.bin
```

更新过程会自动执行：

1. 校验新应用包的完整性和必需文件。
2. 将当前应用包备份为 `bin/knowledge_shelf_query.bin.bak`。
3. 原子替换应用包。
4. 重建容器，使新代码生效，并等待状态接口就绪。
5. 新版本未能正常启动时自动恢复上一版本；成功后显示当前版本。

该过程不会执行 `docker pull`。配置文件、测试单状态和当前工单状态不会被覆盖。

## 五、版本检查与回滚

查看当前应用版本：

```bash
bash start.sh version
```

查看服务日志：

```bash
bash start.sh logs
```

查看 `knowledge_shelf_query` 自身的结构化运行日志（启动、HTTP 请求和处理异常）：

```bash
bash start.sh runtime-logs
```

日志文件位于部署目录的 `logs/knowledge_shelf_query.log`，按 5 MiB 轮转并保留最近 3 个文件；`logs` 与机器人服务的「日志查询」页面相互独立。

新版本异常时回滚：

```bash
bash start.sh rollback
```

回滚会恢复上一个 `.bin` 并重建容器，不需要网络。

## 六、服务重启判定

`restart` 会停止并重建 `knowledge_shelf_query` 容器，可能中断机器人任务；操作前确认设备空闲，并准备重新登录页面。

需要执行 `bash start.sh restart` 或由更新脚本自动重建容器的情况：

- 更新应用包、回滚应用包，或修改应用启动参数。
- 修改 `docker-compose.yml`、`CONFIG_PNP_DIR`、`KNOWLEDGE_DIR`、端口、挂载路径或其他容器环境变量。
- 更换运行时镜像，或修改 Python、Docker CLI、Compose 等运行时依赖。更换镜像时先执行 `pull-runtime`，再执行 `restart`。
- 修改 `config/feishu_rules.json`；规则在服务启动时加载和校验。
- 服务无响应、健康检查失败、启动失败或运行日志持续出现未处理异常。
- `knowledge` 或 `config_pnp` 目录被整体替换、删除后重建或重新挂载。Docker 可能继续绑定旧目录，表现为宿主机有新文件但容器内看不到；重启后还需在页面执行「一键加载」刷新内存数据。

通常不需要重启的情况：只修改已挂载目录中的 knowledge JSON、库位 CSV 或 `config_pnp/config.py`，在页面执行「一键加载」/「重新加载」即可；修改 `config/users.json` 后下一次登录生效。

**更换 Knowledge 根目录才需要重建容器**：把 `KNOWLEDGE_DIR` 改为新的 `model/templates` 根目录后执行 `bash start.sh restart`；同一根目录下更换日期场景只需在页面填写新目录并加载。

快速确认宿主机和容器是否使用同一份目录。「数据加载」页 Knowledge 输入框中的 `knowledge` 表示默认 `/data/knowledge/knowledge`；输入 `.` 时若根下存在默认 `knowledge` 子目录会使用该子目录：

```bash
# 宿主机侧（替换为当前 KNOWLEDGE_DIR）
find /实际/model/templates/knowledge \
  -maxdepth 1 -type f -name '*.json' | wc -l
# 容器侧
docker exec knowledge_shelf_query \
  sh -c "find /data/knowledge/knowledge -maxdepth 1 -type f -name '*.json' | wc -l"
```

两边数量或新文件可见性不一致时，先确认设备空闲，再重启容器并重新加载数据。

## 十、文件管理与显示转发

文件与终端功能仅管理员可用，无需加载业务数据。浏览器资源随应用包交付，设备无需联网下载前端组件，运行镜像无需新增 Python 依赖。

文件和文件夹可通过每行下载按钮旁的重命名图标修改名称；只允许在当前目录内改名，同名目标不会被覆盖。符号链接改名时保留其指向。操作使用 Linux 的原子无覆盖重命名，不支持此操作的系统或文件系统会返回错误。

### 10.1 宿主机与容器

标准 Docker 部署保留网页容器，在宿主机额外运行一个仅使用 Python 标准库的文件与终端连接进程。网页认证、管理员限制和跨站检查仍由现有服务执行，通过挂载的本机 Unix 套接字转发文件和终端请求。该进程无需安装第三方包或单独开放端口，宿主机只需 Python 3.8 或更高版本；可通过 `KSQ_HOST_PYTHON` 指定解释器。

在宿主机部署目录执行 `bash start.sh`，脚本先启动宿主机连接，再启动容器。文件与终端使用启动脚本的系统账号；通过 `sudo` 执行时，使用 `SUDO_USER` 对应的原账号。目录默认打开该账号的主目录，页面显示实际主机和账号。直接以 root 登录运行脚本时仍会使用宿主机 root，可明确设置 `KSQ_HOST_FILES_USER` 为所需的已有账号。部署目录和应用包必须对该账号可读。

宿主机连接目录 `host-files/` 权限为 700，套接字 `host-files/host.sock` 权限为 600，容器通过 `./host-files:/run/ksq-host:ro` 访问。容器配置 `KSQ_HOST_FILES_SOCKET=/run/ksq-host/host.sock`。文件上传、下载、预览和 Shell 全部在宿主机执行；业务数据加载仍沿用原来的容器挂载目录。断开、退出登录和服务停止会回收对应终端。宿主机连接不可用时返回明确错误，不再显示容器的 `/root` 作为替代。

首次升级需同时更新部署目录内的 `start.sh`、`host-files.sh`、`docker-compose.yml` 与 `bin/knowledge_shelf_query.bin`，保留已有 `config/`、`data/`、`logs/` 和环境设置，然后在宿主机执行 `bash start.sh restart`。只更新 `.bin` 或只执行 `docker restart` 不会建立新的连接挂载。

```bash
bash start.sh host-files status   # 查看宿主机账号、主目录和进程
bash start.sh host-files start    # 启动或重启连接进程
bash start.sh host-files stop     # 停止连接进程
```

连接进程随部署启动，终端关闭后仍运行；宿主机重启后需重新执行启动脚本。需要开机自动恢复时，由宿主机已有的 systemd 服务运行 `bash /部署目录/host-files.sh serve`，服务的 `User` 设置为该部署账号。连接日志位于 `host-files/agent.log`。该目录中的 `agent.bin` 是连接进程的代码副本，正常更新时同步；回滚到未包含宿主机连接的旧应用时保留该副本，避免连接进程无法停止。

直接以目标系统账号运行源码或 `.bin` 时，文件和终端仍直接操作宿主机，无需连接进程。源码示例（先激活 Python 3.12 环境）：

```bash
KSQ_HOST=0.0.0.0 KSQ_PORT=8765 bash start.sh
```

`.bin` 也支持直接使用 Python 3.12 执行并传入 `--host`、`--port` 和数据路径参数。选择未被现有服务占用的端口。Shell 继承该进程的账号、`PATH`、`DISPLAY` 等环境；以 root 启动就拥有 root 能力，不建议为此把应用容器改为特权容器。

### 10.2 文字、图片与网页

终端文字、颜色、交互输入在当前浏览器显示，不需设置 `DISPLAY`。保存到服务设备上的图片可从文件管理预览。终端启动的网页服务应监听可达的网卡地址；访问设备使用 `http://设备IP:网页服务端口`。浏览器里的 `127.0.0.1` 指访问设备自身，不能代表远端设备。

### 10.3 GUI 窗口与完整桌面

`Missing X server or $DISPLAY` 表示程序需要图形显示服务。标准部署现已提供独立虚拟桌面：网页终端运行 GUI 程序，页面“远程桌面”在当前访问设备的浏览器标签页显示程序窗口。无需宿主机物理显示器，也不用把 `DISPLAY` 手动设为访问设备 IP。

首次升级需替换 `start.sh`、`host-files.sh`、`docker-compose.yml` 和 `bin/knowledge_shelf_query.bin`。保留现有业务配置，在**宿主机部署目录**执行：

```bash
bash start.sh desktop install
bash start.sh restart
```

安装步骤仅支持 Debian/Ubuntu，通过系统包管理器安装 `tigervnc-standalone-server novnc websockify openbox tint2 xauth dbus-x11 fonts-dejavu-core x11-xserver-utils`，需要安装软件的系统权限和软件源网络连接。同一宿主机只需安装一次，更新应用无需重复安装；换机器或重装系统后需要重新安装。该命令不会更换应用运行时镜像。源码部署使用 `bash devOps/up.sh desktop install` 和 `bash devOps/up.sh restart`。图形窗口最小化后，点击桌面底部任务栏中的程序按钮恢复；也可以按 `Alt+Tab` 切换窗口。

虚拟桌面使用独立的浅色窗口主题、底部任务栏和单个工作区，桌面空白处右键可查看窗口列表。任务栏左键切换或恢复窗口，右键和滚轮不再关闭或最小化程序。样式不会覆盖宿主机账号的桌面配置。旧安装若缺少 `xsetroot`，只影响背景配色，可重新执行安装命令补齐。

升级后刷新文件管理页面，断开并重新连接终端，再重新启动 GUI 程序，点击“远程桌面”查看窗口。连接进程会为终端设置实际虚拟桌面的 `DISPLAY`、`XAUTHORITY` 和独立会话总线；桌面与程序仍由启动脚本的账号运行。不要覆盖这些显示环境变量。未安装组件时，文字终端仍可使用，桌面入口会提示安装命令。

桌面与页面使用同一 IP 和端口，内部地址为 `/desktop/vnc.html`；图形数据经权限为 600 的 Unix 套接字转发，VNC 和 WebSocket 服务不监听额外 TCP 端口。所有桌面资源和连接均检查管理员登录，跨站连接会拒绝，退出登录后已建立的桌面连接也会关闭。已有反向代理需要允许 `/desktop/` 路径及 WebSocket Upgrade；HTTPS 页面使用同一来源的 WSS。

一个部署账号共享一个虚拟桌面，关闭浏览器桌面标签不会结束它；停止或更新宿主机连接进程会关闭虚拟桌面及其程序，重新连接终端时重建。桌面日志位于 `host-files/desktop.log`。这是独立虚拟桌面，不是宿主机物理屏幕的镜像；需要 GPU 加速或依赖物理桌面会话的第三方程序仍须在目标设备上验证。

已有外部 noVNC/Xpra 服务时仍可设置 `KSQ_DESKTOP_URL`（HTTP/HTTPS，不在地址内嵌入凭证）。设置后入口使用外部服务，网页终端保留宿主机连接进程原有的显示环境，不自动切换到内置虚拟桌面；外部服务的显示会话和鉴权由其部署配置负责。使用本节内置桌面时清除旧的 `KSQ_DESKTOP_URL`，然后重建容器。

参考：[TigerVNC Xvnc 参数](https://tigervnc.org/doc/Xvnc.html)、[noVNC 官方说明](https://github.com/novnc/noVNC)。
